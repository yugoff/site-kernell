# Kernell Cloud

Отдельное серверное приложение для `cloud.kernell.ru` в ветке `cloud-portal`.
Основной сайт продолжает собираться из корневого `app/` как статический экспорт.
Cloud использует собственные `app/`, конфигурацию, TypeScript и каталог сборки.
Палитра и типографика совпадают с основным сайтом и версией по мотивам brag: сливочный фон, бордовый маркер, тёмные терминальные блоки, Geist и Geist Mono. Шрифты размещены локально, включая кириллицу; лицензии SIL OFL находятся в `fonts/`. Внешние запросы к Google Fonts для сборки и показа Cloud не требуются.

## Запуск

Нужен Node.js **22.13 или новее в ветке 22**, либо более новая поддерживаемая LTS с `node:sqlite`.
Предупреждение об экспериментальном SQLite в Node 22 ожидаемо.
Команды выполняются из корня репозитория; используются его `package-lock.json` и зависимости.

```bash
npm ci
npm run dev:cloud
```

Открыть http://localhost:3001. Демо доступно по кнопке «Посмотреть кабинет» на главной или «Открыть демокабинет» на странице входа. Каждый посетитель получает отдельный демоаккаунт. Существующий вход в настоящий аккаунт кнопка демо не заменяет.

```bash
npm run check:cloud
npm run build:cloud
npm run test:cloud
npm run start:cloud
```

Интеграционные тесты требуют готовой production-сборки. Они сами запускают сервер на свободном локальном порту с временной базой, проверяют регистрацию, сессии, права доступа, CSRF, черновики заказов, NS-серверы и смену пароля, затем останавливают сервер.

## Что работает

- Витрина, тарифы VPS, пример подбора доменов, адаптивный личный кабинет.
- Регистрация и вход по email/паролю, выход, смена имени и пароля.
- Серверное хранение пользователей, сессий, заказов и истории в SQLite.
- Случайные сессии в HttpOnly/SameSite cookie, в базе хранится SHA-256 хеш токена. Пароли хешируются scrypt с индивидуальной солью. Смена пароля завершает другие сессии.
- Проверка владельца в каждом закрытом API, проверка Origin, ограничение размера JSON и частоты запросов. Данные аккаунта отдаются с `private, no-store`.
- Сохранение заказов с расчётом цены на сервере и ключом идемпотентности. Все новые заказы — **черновики**, не платежи и не активные услуги.
- Изолированное демо: примеры серверов и доменов, запуск/остановка/перезагрузка, NS-серверы, автопродление, история. IP из диапазона документации `192.0.2.0/24`, NS и email — зарезервированные примеры.

## Граница этой версии

Платёжная система и провайдеры **не подключены**. Сайт не принимает реквизиты карты, не списывает средства, не регистрирует домены и не создаёт реальные VPS. Цены и локации предварительные, свободность доменов не проверяется. Демобаланс нельзя потратить или вывести. Формы честно сообщают эти ограничения.

Подтверждение email, почтовое восстановление пароля, платёжные уведомления, фискальные чеки, админка и отправка заказов поставщикам пока не реализованы. Заказ не станет оплаченным от установки переменной окружения: полноценный платёжный и провайдерский контур требуется реализовать отдельно.

Перед публичной регистрацией дополнить политику обработки данных и условия сервиса, настроить подтверждение email/восстановление и эксплуатационное ограничение запросов на reverse proxy. В текущей версии глобальные и email-лимиты защищают вход в рамках небольшого предварительного запуска; глобальный лимит не предназначен для большого публичного трафика.

## Размещение на поддомене

Это Node-приложение с постоянным диском. GitHub Pages и статический Cloudflare Pages для кабинета не подходят. Использовать отдельный процесс или Docker-контейнер; основному сайту изменения хостинга не нужны.

### Обычный Node-процесс

После сборки `npm run start:cloud` копирует статические ресурсы в standalone-сборку и запускает её на `127.0.0.1:3001`. Адрес и порт можно изменить через `CLOUD_HOSTNAME` и `PORT`. Для production задать:

```bash
export CLOUD_ORIGIN=https://cloud.kernell.ru
export CLOUD_DATABASE_PATH=/var/lib/kernell-cloud/cloud.sqlite
export CLOUD_DEMO_ENABLED=true
npm run start:cloud
```

Для разработки переменные также можно задать в `cloud/.env.local` (не попадает в Git). В production передавайте их процессу через окружение или конфигурацию сервиса. Каталог базы должен принадлежать пользователю процесса и находиться на постоянном диске вне каталога релиза. Значение `CLOUD_ORIGIN` — ровно origin без завершающего `/`. В HTTPS-окружении cookie имеет `Secure`. Для локальной проверки production-сборки через HTTP укажите `CLOUD_ORIGIN=http://localhost:3001`.

Добавить DNS-запись `cloud` на адрес сервера, HTTPS-сертификат и reverse proxy с upstream `http://127.0.0.1:3001`. Пример блока Nginx после настройки TLS:

```nginx
location / {
    proxy_pass http://127.0.0.1:3001;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    client_max_body_size 32k;
}
```

### Docker

Собирать из корня репозитория. Для воспроизводимой упаковки копируем только файлы зависимостей и исходники Cloud, не локальную базу:

```bash
docker build -f cloud/Dockerfile -t kernell-cloud .
docker run -d --name kernell-cloud --restart unless-stopped \
  -p 127.0.0.1:3001:3000 \
  -e CLOUD_ORIGIN=https://cloud.kernell.ru \
  -v kernell-cloud-data:/data kernell-cloud
```

Dockerfile проверен по структуре сборки, но Docker-сборка отдельно не запускалась. Next standalone выводится в `cloud/.next/standalone/cloud/server.js`, статические ресурсы копируются отдельно.

Один экземпляр приложения на один локальный SQLite-файл. Для нескольких реплик потребуется внешняя БД и общий ограничитель запросов. Бэкап SQLite выполнять штатным online backup или при остановленном приложении, учитывая WAL; не копировать только основной файл на ходу. Демоаккаунты старше суток удаляются при последующих открытиях демо. Обычные аккаунты автоматически не удаляются.

## Подключение реальных продаж

1. Выбрать и оформить договоры с регистратором и VPS-поставщиком; согласовать тарифы и API-лимиты.
2. Реализовать серверные адаптеры проверки доменов, регистрации/продления/DNS и создания/управления VPS.
3. Добавить платёжный контур с проверкой подписи уведомлений, суммой/валютой из серверного заказа, возвратами и необходимыми чеками.
4. Добавить очередь выдачи, повторные попытки и сверку результата у поставщика перед повторным заказом. Не вызывать покупку прямо из браузера или без подтверждённой оплаты.
5. Сохранять идентификаторы поставщика и отдельно учитывать баланс клиента, его платежи и закупочные списания. Заменить все примерные цены и локации данными договора.

`cloud.kernell.ru` ещё не опубликован: DNS и production-размещение выполняются после выбора сервера. Эта ветка не изменяет production основного сайта.
