# 02. Текущее состояние `cloud/` и анализ пробелов (Gap Analysis)

Документ фиксирует, что уже реализовано в каталоге `cloud/` на текущий момент и чего не хватает для запуска реального реселлерского бизнеса.

## 2. Критический разрыв между текущей версией и продакшн-реселлингом

### 2.1. Инфраструктурные и API-пробелы
1. **Нет универсального Timeweb API-клиента:** сейчас `fetch("https://api.timeweb.cloud/...")` написан точечно внутри `cloud/app/api/domains/check/route.ts`. Нет единого клиента с:
   - обработкой `status_code` / `error_code` / `response_id`,
   - таймаутами, ретраями и соблюдением лимита **20 req/s на endpoint**,
   - логированием обращений к провайдеру.
2. **Нет маппинга «Клиент Kernell ↔ Проект/Ресурсы Timeweb»:** в таблице `services` есть только локальные поля (`id`, `user_id`, `kind`, `name`, `status`, `price`, `renewal`, `details`, `address`, `auto_renew`). Не хранятся:
   - `tw_project_id` клиента,
   - `tw_resource_id` / `tw_fqdn` / `tw_person_id` / `tw_request_id`,
   - реальная закупочная стоимость у Timeweb (`cost_price`) и применённая наценка.
3. **Каталог статичен и покрывает ~5% продуктов:** в `cloud/lib/catalog.ts` зашиты 4 тарифа VPS и 4 доменные зоны. Нет синхронизации с:
   - `/api/v1/presets/servers`, `/api/v1/configurator/servers`, `/api/v1/os/servers`, `/api/v1/software/servers`, `/api/v2/locations`,
   - `/api/v1/tlds` (цены регистрации, продления и трансфера по всем зонам!),
   - остальными 12+ линейками продуктов (БД, S3, K8s, Dedicated, Балансировщики, VPC, Firewall, Плавающие IP, Роутеры, Сетевые диски, Apps, Container Registry, CDN, Почта, AI-агенты/Gateway/Решения).

### 2.2. Биллинг и экономика (главный блокер запуска продаж)
1. **Нет приёма платежей и фискализации:** невозможно пополнить баланс картой/СБП/счётом и получить чек по 54-ФЗ.
2. **Нет финансового леджера (журнала проводок):** в `accountFor()` баланс возвращается константой `user.demo ? 2480 : 0`. Нужны неизменяемые проводки (пополнение, резервирование, почасовое/помесячное списание, возврат).
3. **Нет биллинг-движка для почасовых облачных услуг:** Timeweb списывает за облачные серверы, БД, S3, K8s и сеть **почасово** (или помесячно), а за домены и dedicated — **единовременно за период** (`P1Y`, `P1M`...). Kernell должен уметь:
   - списывать предоплату за период или вести регулярные списания с кошелька клиента,
   - останавливать/блокировать ресурс при уходе баланса клиента в ноль,
   - удалять неоплаченные ресурсы после grace-периода, чтобы мастер-аккаунт Kernell не продолжал платить за них Timeweb.
4. **Нет мониторинга мастер-баланса:** если на партнёрском аккаунте Kernell в Timeweb закончатся деньги (`hours_left` → 0, `is_blocked: true`), Timeweb заблокирует **все** серверы **всех** клиентов сразу.

### 2.3. Асинхронный жизненный цикл и операции
1. **Нет очереди задач (job queue) / воркера синхронизации:** создание VPS, БД, K8s-кластера или регистрация домена в Timeweb происходят асинхронно (`installing`, `creating`, `registration_request`). Нужно фоново отслеживать статус, дожидаться выдачи IP/`root_pass`/завершения заявки и обновлять кабинет клиента.
2. **Нет обработчика вебхуков Timeweb:** необходимо endpoint-приёмник событий от Timeweb (с проверкой подписи) + резервный поллинг.
3. **Нет управления реальными услугами:** `POST /api/services/[id]` жёстко возвращает `503` для всех реальных пользователей (`if (!user.demo) throw new ApiError(503, ...)`).

### 2.4. Аккаунт, безопасность и UX перед открытием продаж
1. **Нет подтверждения email и восстановления пароля:** при потере пароля клиент не может восстановить доступ к оплаченным серверам и доменам (указано даже в UI настроек и `cloud/README.md`).
2. **Нет сбора и шифрования анкет администратора домена (`persons`):** для `.ru`/`.рф` нужны паспортные данные/ИНН/КПП, их нельзя хранить открытым текстом без шифрования.
3. **Нет системы поддержки/тикетов в кабинете:** сейчас только `mailto:info@kernell.ru`. Для реального хостинг-провайдера нужны тикеты с привязкой к `service_id`, чтобы при проблемах на стороне Timeweb поддержка Kernell могла быстро передавать в Timeweb `response_id` / ID ресурса.
4. **Ограничение одного инстанса SQLite:** текущая `node:sqlite` идеальна для прототипа и 1 процесса, но при появлении фоновых биллинг-воркеров, очередей провижининга и вебхуков оплаты стоит запланировать переход на PostgreSQL (или чёткую изоляцию единого воркера/блокировок на раннем этапе).
