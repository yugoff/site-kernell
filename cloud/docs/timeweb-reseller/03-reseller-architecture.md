# 03. Целевая архитектура реселлерской платформы Kernell Cloud

Этот документ описывает техническую архитектуру, необходимую для безопасной перепродажи всех сервисов Timeweb Cloud под брендом **Kernell Cloud**.

---

## 1. Модель мультитенантности (Tenant Isolation)

В публичном API Timeweb Cloud **нет субаккаунтов** — все ресурсы создаются внутри одного реселлерского аккаунта Kernell (`TIMEWEB_TOKEN`). Поэтому изоляция клиентов полностью строится на двух уровнях:

### Уровень A: Проектная изоляция в Timeweb (`/api/v1/projects`)
Для каждого клиента (или рабочего пространства) Kernell создаёт отдельный проект в Timeweb (`POST /api/v1/projects`) и сохраняет `tw_project_id` в таблице `workspaces` / `users`.

**14 типов ресурсов поддерживают `project_id` уже при создании (`POST`):**
- Облачные серверы (`/api/v1/servers`)
- Выделенные серверы (`/api/v1/dedicated-servers`)
- Облачные БД (`/api/v1/databases`)
- Kubernetes-кластеры (`/api/v1/k8s/clusters`)
- S3-бакеты (`/api/v1/storages/buckets`)
- Балансировщики (`/api/v1/balancers`)
- App Platform (`/api/v1/apps`, `/api/v2/apps`)
- Реестр контейнеров (`/api/v1/container-registry`)
- CDN-ресурсы (`/api/v1/cdn/http-resources`)
- Роутеры (`/api/v1/routers`)
- AI Агенты (`/api/v2/cloud-ai/agents`), Базы знаний (`/api/v1/cloud-ai/knowledge-bases`), AI-ключи (`/api/v1/cloud-ai/ai-keys`), AI-решения (`/api/v1/cloud-ai/solutions`)

> Если ресурс по какой-то причине создан без `project_id`, его можно перенести в проект методом `PUT /api/v1/projects/{project_id}/resources/transfer` или `POST /api/v1/projects/{project_id}/resources/{type}`.

### Уровень B: Аккаунт-глобальные ресурсы (строгий Ownership в БД Kernell)
Следующие ресурсы в Timeweb Cloud **не привязаны к `project_id`** и живут на уровне всего мастер-аккаунта:
- **Домены, заявки и администраторы доменов:** `domains`, `domains-requests`, `persons` (включая ПДн!).
- **Почта:** `mail/domains/{domain}`.
- **Приватные сети (`vpcs`):** `/api/v2/vpcs`.
- **Firewall-группы:** `/api/v1/firewall/groups`.
- **Сетевые диски (`network-drives`) и плавающие IP (`floating-ips`).**
- **SSH-ключи (`ssh-keys`), пользовательские образы (`images`), VCS-провайдеры (`vcs-provider`).**
- **S3-администраторы (`GET /api/v1/storages/users`):** **КРИТИЧНО!** Этот эндпоинт возвращает пользователей хранилища уровня всего аккаунта Timeweb. Никогда не вызывайте его для конечного клиента! Вместо этого используйте собственные `access_key` и `secret_key`, которые Timeweb возвращает внутри каждого конкретного объекта `bucket` (`POST /api/v1/storages/buckets`).

**Железное правило:** клиентский API Kernell **никогда** не должен делать `GET /api/v1/servers` или `GET /api/v1/domains` с возвратом сырого списка Timeweb пользователю. Все списки строятся из БД Kernell по `WHERE user_id = ?` (или `workspace_id = ?`), а перед любым действием (`start`, `dns`, `delete`, `bind`, `mount`) сервер проверяет владение как целевым ресурсом, так и привязываемым ресурсом (например, что `floating_ip`, `vpc_id` или `ssh_key_id` принадлежат тому же клиенту!).

## 2. Ценообразование, маржа и биллинг

### 2.1. Синхронизация прайса и правила наценки
Нельзя держать тарифы захардкоженными в `catalog.ts` после запуска продаж:
- Фоновый джоб (раз в 15–60 минут) тянет актуальные справочники Timeweb:
  - `GET /api/v1/tlds` (стоимость регистрации, продления, трансфера, whois-privacy)
  - `GET /api/v1/presets/servers`, `/api/v1/configurator/servers`, `/api/v1/os/servers`, `/api/v1/software/servers`
  - `GET /api/v2/presets/dbs`, `/api/v1/configurator/databases`, `/api/v1/database-types`
  - `GET /api/v1/presets/k8s`, `/api/v1/presets/storages`, `/api/v1/presets/balancers`, `/api/v1/presets/dedicated-servers`, `/api/v1/presets/apps`, `/api/v1/cdn/presets`, `/api/v1/container-registry/presets`, `/api/v1/presets/routers`, `/api/v1/presets/network-drives`, `/api/v2/locations`, `/api/v3/cloud-ai/models`, `/api/v1/cloud-ai/token-packages/*`
- На уровне Kernell хранится **таблица правил наценки (`pricing_rules`)**:
  - можно задавать % наценки или фиксированную розничную цену по категории / локации / пресету;
  - на старте обязательно учитывать комиссии эквайринга (2–3.5%) + налоги (УСН/ОСНО/НДС) + риск неоплаченных часов;
  - в каждом заказе и подписке сохраняется **снимок цен** (`cost_price_snapshot`, `retail_price_snapshot`, `margin_snapshot`).

### 2.2. Модель кошелька и две схемы тарификации
Timeweb тарифицирует разные продукты по-разному, поэтому биллинг Kernell должен поддерживать обе модели:

1. **Единоразовая оплата за период (Prepaid Term):**
   - **Домены** (`P1Y`..`P10Y`, для `.ru`/`.рф` 1–3 года), **Выделенные серверы** (`P1M`, `P3M`, `P6M`, `P1Y`), **Пакеты токенов AI** (`add-additional-token-package`).
   - Схема: клиент оплачивает заказ полностью → средства списываются в леджер → создаётся и оплачивается ресурс у Timeweb.
2. **Подписочные / почасовые облачные ресурсы (VPS, БД, K8s, S3, Балансировщики, Плавающие IP, Сетевые диски, Роутеры, CDN, Apps):**
   - **Рекомендуемая схема для старта (Monthly Prepay / Credit Wallet):**
     - При создании услуги с кошелька клиента сразу списывается плата за первый расчётный период (например, 1 месяц или 7 дней минимум) или выполняется почасовое/ежедневное списание из авансового баланса.
     - Преимущество месячной/недельной предоплаты перед чистым `pay-as-you-go`: вы не попадаете на кассовый разрыв и фрод с «одноразовыми серверами на 1 час».
   - **Контроль задолженности клиента (Dunning & Lifecycle):**
     - `T - 3 дня`, `T - 1 день`: email/уведомление в кабинете о скором списании.
     - `Balance < next_charge`: статус в Kernell = `suspended` → для VPS/БД/Apps отправляется остановка (`shutdown` / `pause`), доступ к управлению замораживается (внимание: в Timeweb выключенный сервер **продолжает списывать деньги за диск, IP и ресурсы**!).
     - `Grace period` (например, 3–7 дней при `suspended`): клиент может пополнить баланс и восстановить работу.
     - По истечении grace-периода: автоматическое удаление ресурса в Timeweb (`DELETE /api/v1/...`), чтобы остановить списание с партнёрского мастер-аккаунта!

### 2.3. Финансовый леджер (Ledger)
Нельзя менять баланс простым `UPDATE users SET balance = balance + X`:
- Используйте таблицу **`ledger_entries`** (`id`, `user_id`, `amount_kopecks`, `direction` (`credit`/`debit`), `kind` (`topup`, `order_charge`, `renewal_charge`, `refund`, `adjustment`), `reference_type`, `reference_id`, `idempotency_key`, `created_at`).
- Баланс вычисляется атомарно в транзакции с `balance_cache` (в копейках `INTEGER`, никаких `float` для денег!).

### 2.4. Защита мастер-аккаунта партнёра
- Фоновая задача каждые 5–10 минут опрашивает `GET /api/v1/account/finances` и `GET /api/v1/account/status`.
- Пороги тревоги (Telegram/email админам):
  - `hours_left < 72` (менее 3 суток работы облака) — предупреждение;
  - `hours_left < 24` — критический алерт;
  - `is_blocked === true` или `is_permanent_blocked === true` — немедленный стоп создания новых заказов (`503`) и экстренный алерт.
- Сверка расходов (`GET /api/v1/account/services/cost`) сопоставляет активные платные ресурсы в Timeweb с активными подписками в БД Kernell — выявляет «осиротевшие» (orphan) ресурсы, за которые Timeweb ещё списывает, а клиент Kernell уже не платит.

## 3. Асинхронный провижининг, вебхуки и поллинг

Создание большинства ресурсов в Timeweb асинхронно:
- `POST /api/v1/servers` возвращает `201 Created`, но `status` = `"installing"`, `root_pass` может быть ещё `null`, публичный IP может появиться чуть позже.
- `POST /api/v1/domains-requests` создаёт заявку, которую затем нужно оплатить отдельным запросом `PATCH /api/v1/domains-requests/{request_id}` (`{ "money_source": "use" }`), и регистрация в реестре занимает время (`registration_request` → `paid`).
- `POST /api/v1/dedicated-servers` при `autoinstall_ready === 0` устанавливается инженерами вручную (не моментально!).

### Архитектура выполнения заказов
1. **Outbox / Job Queue (`provisioning_jobs`):**
   - После подтверждения оплаты создаётся задача провижининга в состоянии `queued`.
   - Воркер берёт задачу, ставит lock, выполняет API-цепочку в Timeweb с учётом rate limit (**<= 20 req/s на endpoint**).
   - При сетевом сбое / 5xx / 429 — экспоненциальный backoff с проверкой уже созданных объектов, чтобы не создать дубль сервера при повторной попытке.
2. **Двухконтурная синхронизация статусов:**
   - **Вебхуки Timeweb:** настраиваются вручную в панели управления Timeweb Cloud (до 20 вебхуков на аккаунт; в API методов управления вебхуками нет). Эндпоинт Kernell (`POST /api/webhooks/timeweb`) проверяет секретный заголовок подписи, сразу отвечает `2xx` и ставит обновление ресурса в очередь.
   - **Фоновый поллинг:** каждые 15–30 сек опрашивает ресурсы в переходных статусах (`installing`, `reinstalling`, `turning_on`, `turning_off`, `rebooting`, `creating`, `registration_request`, `prolongation_request`, `transfer_request`), и раз в 5–15 минут — фоновая сверка.

## 4. Безопасность, 152-ФЗ и база данных

1. **Шифрование секретов и ПДн на уровне приложения (AES-256-GCM):**
   - Анкеты администраторов доменов (`persons`: паспортные данные, ИНН, адреса, телефоны).
   - Учётные данные выданных услуг (`root_pass`, `vnc_pass`, `ipmi_password`, S3 `secret_key`, пароли админов БД, `kubeconfig`, токены AI-ключей).
   - Ключ шифрования хранится вне БД (`CLOUD_DATA_ENCRYPTION_KEY`), с поддержкой ротации (`key_version`).
2. **Обязательные функции безопасности аккаунта:**
   - Подтверждение email при регистрации / смене почты.
   - Восстановление пароля по одноразовому токену с коротким TTL.
   - Двухфакторная аутентификация (TOTP) как минимум для админов и опционально для клиентов (защита от несанкционированного удаления серверов/доменов).
   - Журнал аудита всех критических действий (кто, с какого IP, когда удалил сервер, сменил NS, сбросил root-пароль).
3. **База данных (SQLite → PostgreSQL):**
   - Текущая `node:sqlite` достаточна для прототипа и одного процесса, но при запуске реального биллинга, вебхуков эквайринга, фонового поллера и горизонтального масштабирования **необходим переход на PostgreSQL** (транзакции `SERIALIZABLE`/`READ COMMITTED` + `SELECT ... FOR UPDATE` на балансах и задачах провижининга, отсутствие блокировки записи файла SQLite).
4. **Конфигурация Next.js:**
   - На сервере должна быть переменная `TIMEWEB_TOKEN` (и при необходимости раздельные ключи / секреты вебхуков).
   - При наличии платных покупок отключить или строго изолировать демо-режим (`CLOUD_DEMO_ENABLED=false` или чёткое разделение в интерфейсе).
